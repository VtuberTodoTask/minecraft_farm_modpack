# 経済設計

憲法は CLAUDE.md 2.3。ここではその運用方法を書く。
数値そのものは `data/prices.yaml` が唯一の正であり、このドキュメントは
「どう決めるか」だけを扱う。

## 原則

### 金は農業からしか湧かない

収入源は次の4つに限る。

| 収入源 | 対応する mod | 位置づけ |
|---|---|---|
| 作物の納品 | Croptopia ほか | 序盤の主収入。単価は低い |
| 料理の納品 | Farmer's Delight | 中盤以降の主収入。加工で単価が跳ねる |
| 釣果の納品 | Aquaculture 2 | 雨天・冬の代替収入 |
| 日替わり依頼 | Bountiful | 変動収入。作物と料理の需要を揺らす |

畜産の一次産物（卵・牛乳・羊毛）は買取に含めてよいが、モブドロップ
（骨・糸・火薬・エンダーパール等）は含めない。前者は動物を飼う手間が
かかり続けるのに対し、後者はトラップで無限に自動化できるため。

### 鉱物は買うものであり続ける

鉱石は自然生成しない（憲法 2.2）。したがって鉱物の唯一の入手経路は
ショップからの購入になる。ここに買取を作ってはいけない。作った瞬間に

    鉱物を買う → 加工する → 売る

という閉ループができ、Create で自動化された時点で無限金策になる。

この制約は文章だけでは守れないので、`scripts/gen_quests.py` が
`data/prices.yaml` を機械的に検査して、鉱石・インゴット・モブドロップが
買取側に混ざっていたらエラーで止まるようにしてある。
カテゴリ名だけでなくアイテムIDの見た目でも弾く。

### 売りと買いに同じ物を置かない

差額で稼げてしまう。これも `gen_quests.py` が検査する。

## 価格の決め方

**未決定**。CLAUDE.md 7章「料理納品の時給想定」が決まっていないため、
`data/prices.yaml` の価格は1つも入っていない。

決めるべきものは1つだけで、あとはそこから機械的に降りてくる。

1. **基準時給を決める**（`baseline.target_income_per_hour`）

   「畑を一通り回して納品する1時間で何コイン稼げるか」。
   これが決まると、序盤の畑の規模から作物1個あたりの単価が逆算できる。

2. **加工の倍率を決める**

   生の作物より料理のほうが高く売れる。この比が「加工する動機」の強さになる。
   低すぎると誰も料理せず、高すぎると作物の納品が無意味になる。

3. **購入価格を時間で表す**

   鉄インゴット1個の価格は「畑で何分ぶん」かで考える。
   温室（グリーンハウスガラス）は中盤の主要目標なので高く置く（憲法 2.4）。

### 決めるときに一緒に考えること

- **冬をどう扱うか**。冬に収入が落ちること自体は狙いどおり（憲法 2.4）だが、
  落ちすぎると詰む。釣りと畜産と依頼で冬の最低収入を作れるか確認する。
- **季節限定作物の割増**。旬のものを高く買うと季節を意識する理由になる。
- **Bountiful の依頼報酬**との釣り合い。依頼のほうが割がよすぎると
  通常の納品が死ぬ。

## 販売の実装方式

**未決定**。CLAUDE.md 5.4 のとおり、FTB Quests のリピートクエストには
報酬を再取得できる／チームで複製される不具合が知られている。

再現テストの結果しだいで方式が変わり、方式が変われば生成する SNBT の
構造も変わる。そのため `scripts/gen_quests.py` は検査までしか実装していない。
経緯は `docs/decisions.md` に残すこと。
